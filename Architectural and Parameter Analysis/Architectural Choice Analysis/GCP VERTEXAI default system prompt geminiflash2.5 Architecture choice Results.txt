Question: What if there are everyone boosting QoD?

Response:

Nokia Network-as-Code (NaC) Quality on Demand (QoD) is designed to manage and prioritize network resources, not to create unlimited bandwidth. Here's what happens if many users request QoD boosts:

1.  **QoS Profiles:** QoD operates using predefined Quality of Service (QoS) profiles. These profiles specify parameters like uplink and downlink speeds. Network operators define these profiles to ensure that even when a boost is requested, it aligns with the network's overall capacity and management policies.
2.  **Shared Resources:** Networks are shared resources. QoS is used to manage and prioritize the flow of data, especially during heavy traffic. It ensures that critical services or applications receive preferential treatment according to demand, but it doesn't magically increase the network's physical capacity.
3.  **Network Management:** If everyone were to request a QoD boost simultaneously, the network's underlying infrastructure would still have finite resources. The system is designed to prevent a complete free-for-all that would lead to overall network degradation. Network operators manage these resources to prevent unfairness, congestion, or a situation where boosting one user severely impacts others.
4.  **Prioritization, Not Guarantee of Absolute Speed:** QoD ensures that your traffic is prioritized over non-boosted traffic. However, it cannot guarantee absolute speeds if the network is severely congested or if the requested profile exceeds the physical capabilities of the network at that specific location and time. The goal is a more consistent and reliable user experience for prioritized traffic.

In essence, while QoD allows applications to request enhanced network performance, it operates within the constraints and management policies of the network to maintain overall stability and fairness.

Question: Why do I need to include private, public IP addresses and port when creating a QoD session?

Response:

When creating a Quality on Demand (QoD) session with Nokia Network-as-Code (NaC), you need to include the private IP address, public IP address, and public port for accurate device identification and to correctly program the network.

Here's why these details are necessary:

1.  **Accurate Device Identification:** Mobile networks frequently use Network Address Translation (NAT). This means a device might have a private IP address within the mobile operator's network, and its traffic is then translated to a public IP address and a specific public port when communicating with external services.
2.  **Distinguishing Devices Behind NAT:** If multiple devices share the same public IP address (due to NAT), the combination of the public IP address and the public port is essential to uniquely identify the specific device's connection. The documentation states that devices cannot be identified by their public IPv4 address alone; you need to provide either their public address and port or public and private addresses.
3.  **Programming the Network:** A QoD session instructs the network to prioritize traffic between a specific device and an application server. To do this effectively, the network needs precise information about both endpoints. By providing the public IP, private IP, and public port, you enable the NaC platform to correctly identify the device's network path and apply the requested Quality of Service profile to the intended traffic flow.

This detailed identification ensures that the network programming for QoD is applied to the correct device and its specific connection, optimizing bandwidth and latency as requested.

Question: How does network as code handle end-user consent?

Response:

Nokia Network-as-Code (NaC) adopts a privacy-by-design approach and is built to comply with data protection regulations like GDPR. Therefore, handling end-user consent is a critical aspect of how NaC operates. Consent management in NaC is about granting or revoking an application's access to APIs and their parameters, ensuring that authorized devices can be safely used.

Here's how NaC handles end-user consent:

**1. Why Consent is Needed:**
Applications often need to process personal or private enterprise information. To do so with "legitimate interest" and a legal basis, consent (authorization) from device owners is required. This allows a device's owner to control which applications or APIs can access their device.

**2. Key Terminology:**
*   **Scope:** Defines the feature or operation that is authorized (e.g., `location-retrieval`, `qod-sessions`). It can be extended with specific resources or actions like "read" or "write."
*   **Device ID:** The identifier for the device or subscriber in the network (e.g., a phone number like `36721601234567` or an email-like identifier `device@testcsp.net`).
*   **Authorized Party:** The private enterprise, organization, or system integrator that will be authorized to use the devices within the defined scopes.
*   **Operator:** The owner of a network that can be used through the NaC APIs.

**3. Consent in Business to Business (B2B) Scenarios:**
In B2B scenarios, such as an enterprise managing multiple mobile devices (e.g., for drones in agriculture), consent is typically managed by an **Organization Admin**.
*   **Authorization Request:** The Organization Admin fills out a "Nokia Network as Code Consent & Authorization template" (an Excel spreadsheet). This form specifies:
    *   The legal name of the authorizing organization.
    *   The authorized party (the organization gaining access).
    *   The date of consent.
    *   A list of **Device IDs** (phone numbers or external identifiers).
    *   The **Scopes** (API functionalities) being authorized for each device.
    *   The **Operator** from whom the mobile subscription is held.
    *   A **Revocation Date** for each consent.
*   **Submission and Validation:** The Organization Admin sends this request via email to `support.networkascode@nokia.com`. The NaC Admin then validates the form data with the listed operators and enables the specified organizations to access their allowed devices and scopes.
*   **Managing Changes:** Submitting a new request completely cleans up the previous one. Devices not included in the new list will lose their authorization.

**4. Consent in Business to Consumer (B2C) Scenarios (e.g., Number Verification):**
For B2C interactions, NaC often uses a **3-legged OAuth 2.0 flow**, where a network subscriber (the device end-user) gives consent through a Network Provider interface.
*   **Authorization URL:** A mobile application initiates a verification (e.g., phone number verification) by requesting and receiving an authorization URL.
*   **User Interaction:** The end-user must access this URL via a mobile connection. This typically involves several redirects to an operator-specific web portal where the user can provide their consent.
*   **Callback:** Upon successful consent, a `GET` request is triggered back to the application's redirect URI, containing an NaC authorization code.
*   **SDK Simplification:** NaC SDKs simplify this process by automatically issuing intermediate requests on behalf of the developer to collect necessary information for constructing valid authorization requests.

**5. End-User Consent Flows:**
NaC utilizes different consent flows depending on the interaction:
*   **Client Initiated Backchannel Authentication (CIBA) flow:**
    *   Used in simpler cases where NaC handles requests for the end-user.
    *   NaC polls an Authorization Server, which is responsible for triggering an appropriate end-user consent request (approve or deny).
    *   Once approved, the Authorization Server provides a client token.
    *   This flow is largely transparent to the application developer, as the NaC runtime handles the polling.
*   **Authorization Code flow:**
    *   Used when the end-user needs to take positive action to indicate consent.
    *   The application developer constructs an authorization URL (pointing to the NaC authorization server and including their own redirect handler) and directs the end-user application to it.
    *   NaC redirects the user to their operator-specific consent portal.
    *   If consent is given, the application is redirected back to its redirect URI with an operator code, which is then exchanged for a single-use access token.

**6. Application Registration and Consent Screenshots:**
To ensure compliance, applications must go through a registration process.
*   **Information Submission:** Developers submit information about their business and the network capabilities they intend to use.
*   **Consent Request Screenshots:** Applications are expected to ask for end-user consent for actions related to personal information (e.g., location data, phone number). Developers must provide screenshots of each step in their application's consent request flow. These screenshots are submitted to network operators to validate compliance with data privacy legislation in target countries.

**7. Specifying Purpose:**
For some APIs, a valid purpose must be dynamically specified (e.g., `dpv:FraudPreventionAndDetection`). This explains *why* authorization is being requested. A purpose can be associated with a scope (e.g., `dpv:FraudPreventionAndDetection number-verification:verify`). For APIs other than Number Verification, NaC automatically supplies the purpose specified during application registration. If a new purpose is needed, developers must notify NaC support.

By implementing these mechanisms, Nokia Network-as-Code ensures that network capabilities are exposed and utilized in a secure and privacy-compliant manner, respecting end-user consent.

Question: What do I need to do to my application in order to be able to receive notifications from Network as Code?

Response:

To receive notifications from Nokia Network-as-Code (NaC), you need to configure your application to act as a webhook receiver. This involves setting up an HTTP endpoint (a "notification URL") that NaC can send `POST` requests to, along with an optional authentication token for security.

Here's what you need to do:

1.  **Set up a Notification URL (Webhook Endpoint):**
    Your application needs to expose an HTTP endpoint that can listen for incoming `POST` requests. This endpoint will be the `notification_url` you provide when subscribing to events in NaC. The exact implementation can be handled by developers as they see fit.

    **Example (Python using FastAPI):**
    ```python
    from fastapi import FastAPI, Header
    from pydantic import BaseModel
    from typing import Union, Annotated

    app = FastAPI()

    # Define the structure of the incoming notification
    class Data(BaseModel):
        # Example data structure, this will vary based on notification type
        device: dict | None = None
        subscriptionId: str | None = None
        roaming: dict | None = None # For roaming notifications
        # ... other fields depending on the notification type

    class Notification(BaseModel):
        id: str
        source: str
        type: str
        specversion: str
        datacontenttype: str
        time: str
        data: Data # The actual payload of the notification

    @app.post("/notifications")
    def receive_notification(
        notification: Notification,
        authorization: Annotated[Union[str, None], Header()] = None
    ):
        # Validate the authorization token if one is expected
        if authorization == "Bearer my-token": # Replace "my-token" with your actual token
            # Process the incoming notification
            print("Received notification:")
            print(notification)
            # You can now react to the notifications based on the Notification object
            return {"status": "Notification received and processed"}
        else:
            # Handle unauthorized access
            print("Unauthorized notification attempt.")
            return {"status": "Unauthorized"}, 401

    # To run this: save as, e.g., `main.py` and run `uvicorn main:app --reload`
    ```

    **Example (TypeScript using Express.js):**
    ```typescript
    import express, { Express, Request, Response } from "express";

    const app: Express = express();
    const port = process.env.PORT || 3000;

    app.use(express.json()); // Middleware to parse JSON request bodies

    // Define the structure of the incoming notification (example for device status)
    interface DeviceStatusNotification {
        id: string;
        source: string;
        type: string;
        specversion: string;
        datacontenttype: string;
        time: string;
        data: {
            device: {
                phoneNumber?: string;
                networkAccessIdentifier?: string;
                ipv4Address?: {
                    publicAddress?: string;
                    privateAddress?: string;
                    publicPort?: number;
                };
                ipv6Address?: string;
            };
            subscriptionId: string;
            terminationReason?: string;
        };
    }

    app.post("/notifications", (req: Request, res: Response) => {
        // Check for authorization header if you've configured one
        const authorizationHeader = req.headers.authorization;
        if (authorizationHeader === "Bearer my-token") { // Replace "my-token"
            const notification: DeviceStatusNotification = req.body;
            // We can now use the notification object to react to changes
            console.log("Received notification:", notification);
            res.status(200).end(); // Acknowledge receipt
        } else {
            console.log("Unauthorized notification attempt.");
            res.status(401).send("Unauthorized");
        }
    });

    app.listen(port, () => {
        console.log(`[server]: Server is running at http://localhost:${port}`);
    });
    ```

2.  **Provide a Notification Authentication Token (Optional but Recommended):**
    When you subscribe to notifications, you can also provide a `notification_auth_token`. This token will be included in the `Authorization` header of the `POST` request sent by NaC to your notification URL (e.g., `Authorization: Bearer my-token`). Your application should validate this token to ensure that the notification is coming from a trusted source.

3.  **Subscribe to Notifications using NaC SDK:**
    When you perform an action or subscribe to an event using the NaC SDK, you will pass your `notification_url` and `notification_auth_token`.

Certainly! Here's a Python code example that demonstrates how to create a Quality on Demand (QoD) session using the Nokia Network-as-Code (NaC) SDK. This example includes initializing the client, identifying a device, and then creating a QoD session with a specified duration and QoS profile.

```python
import network_as_code as nac
from network_as_code.models.device import DeviceIpv4Addr

# 1. Initialize the Network as Code client
# Replace "YOUR_APPLICATION_KEY" with your actual application key from the NaC Dashboard.
client = nac.NetworkAsCodeClient(token="YOUR_APPLICATION_KEY")

# 2. Identify the mobile network device
# Devices can be identified by various means. Here, we use IPv4 address details
# and a phone number. Remember that devices cannot be identified by their public
# IPv4 address alone; you need to provide either their public address and port
# OR public and private addresses.
device = client.devices.get(
    ipv4_address=DeviceIpv4Addr(
        public_address="1.1.1.2",  # Example public IPv4 address
        private_address="1.1.1.2", # Example private IPv4 address (can be same as public for simplicity in some cases)
        public_port=80             # Example public port
    ),
    # The phone number does not accept spaces or parentheses
    phone_number="+36721601234567" # Example phone number
)

# 3. Create a QoD session for the identified device
# This creates a session with a specific QoS profile, targeting an application server,
# and with a defined duration.
# - service_ipv4: The IPv4 address of the application server that will benefit from the QoD.
# - profile: The QoS profile (e.g., "QOS_L" for low latency, "QOS_M" for medium, "QOS_H" for high).
# - duration: The length of the QoD session in seconds (mandatory).
qod_session = device.create_qod_session(
    service_ipv4="5.6.7.8",  # Example IPv4 address of the application server
    profile="QOS_L",         # Example QoS profile (e.g., Low Latency)
    duration=3600            # Session duration in seconds (1 hour)
)

# 4. Print the details of the created QoD session
print(f"QoD Session Created:")
print(f"  Session ID: {qod_session.session_id}")
print(f"  QoS Status: {qod_session.qos_status}")
print(f"  Profile: {qod_session.qos_profile}")
print(f"  Duration: {qod_session.duration} seconds")
print(f"  Expires At: {qod_session.expires_at}")

# You can also extend the session duration later if needed:
# qod_session.extend(300) # Extends the session by another 300 seconds (5 minutes)
# print(f"QoD Session Extended. New expiration: {qod_session.expires_at}")
```

Question: How do I interpret the network insights API response?

Response:

The Nokia Network-as-Code (NaC) Network Insights API provides valuable data about network conditions and device states. Interpreting the responses from these APIs depends on the specific insight you are querying, such as congestion levels or device location verification.

Here's how to interpret responses from key Network Insights functionalities:

### 1. Congestion Levels API Response

The Congestion Levels API allows you to poll for current, historical, or predictive congestion data for a device.

**a. Polling Current Congestion Levels:**
When you poll for the current congestion level, the API returns an array of congestion level objects.
*   **`level`**: This is the primary indicator, which can be one of the following string values:
    *   `"None"`: No congestion detected.
    *   `"Low"`: Low level of network congestion.
    *   `"Medium"`: Medium level of network congestion.
    *   `"High"`: High level of network congestion.

    **Example Output (Python):**
    ```
    High
    ```
    (Source: https://developer.networkascode.nokia.io/docs/network-insights/congestion-levels)

**b. Getting Predictions or Historical Data:**
When requesting congestion data between two timestamps, the API returns an array of `Congestion` objects, each providing a specific time window and a confidence level for predictions.
*   **`start`**: An ISO 8601 formatted date string indicating the beginning of the time period for which the congestion level applies.
*   **`end`**: An ISO 8601 formatted date string indicating the end of the time period for which the congestion level applies.
*   **`level`**: The predicted or historical congestion level for that period, using the same values as above (`"None"`, `"Low"`, `"Medium"`, `"High"`).
*   **`confidence`**: A numeric value from 0 to 100, representing the percentage confidence in the prediction. This is particularly useful for predictive data.

    **Example Output (Python for prediction):**
    ```
    2024-09-09T11:09:52.950638
    2024-09-09T11:11:30.950638
    High
    75
    ```
    This indicates that between the `start` and `end` timestamps, the congestion level is predicted to be "High" with a 75% confidence.
    (Source: https://developer.networkascode.nokia.io/docs/network-insights/congestion-levels)

**c. Congestion Notification Details (Webhook Payload):**
If you subscribe to congestion notifications, your configured `notificationUrl` will receive `JSON` objects with the following structure:
*   **`id`**: A string value representing the event subscription identifier.
*   **`source`**: A string identifying the source of the event, including the NaC API implementation and subscription ID.
*   **`type`**: A string value returned by the API with different statuses (e.g., "event").
*   **`specversion`**: A string representing the specification version.
*   **`datacontenttype`**: Indicates the media type for the event payload encoding, typically "application/json".
*   **`time`**: An ISO 8601 formatted date string indicating when the event occurred.
*   **`data`**: An object containing the actual congestion level data.
    *   **`data.level`**: The congestion level, which can be `"none"`, `"low"`, `"medium"`, or `"high"`.

    **Example JSON Schema for Congestion Notification:**
    ```json
    {
      "id": "2628b42e87894fcd942a841f16f52897",
      "source": "org.camaraproject.congestioninsights.v0.event",
      "type": "event",
      "specversion": "1.0",
      "datacontenttype": "application/json",
      "time": "2025-04-18T12:54:21.495311",
      "data": {
        "level": "Medium"
      }
    }
    ```
    (Source: https://developer.networkascode.nokia.io/docs/network-insights/congestion-schema)

### 2. Location API Response (Verifying Device Location)

The `POST verifyLocation` endpoint returns a `JSON` object that indicates whether a device is within a specified geographical area.
*   **`verificationResult`**: This is the primary result, indicating the device's location status relative to the defined area. It can be:
    *   `"TRUE"`: The device is within the circle defined by its center location and radius.
    *   `"FALSE"`: The device is outside the defined circle.
    *   `"PARTIAL"`: The device's location partially overlaps with the defined circle. In this case, `matchRate` will also be included.
    *   `"UNKNOWN"`: No historical location data is available for the device. In this case, `lastLocationTime` will not be provided.
*   **`lastLocationTime`**: An ISO 8601 formatted date-time string indicating the timestamp of the last known location information for the device. This is not provided if `verificationResult` is `"UNKNOWN"`.
*   **`matchRate`**: An integer value (1-99) included *only* when `verificationResult` is `"PARTIAL"`. It estimates the percentage match between the requested area and the area where the network locates the device. It's calculated as `(R ∩ N) / N * 100`, where R is the requested area and N is the network-located area.

    **Example Response (TRUE):**
    ```json
    {
      "verificationResult": "TRUE",
      "lastLocationTime": "2025-02-11T08:00:41.665176Z"
    }
    ```
    **Example Response (PARTIAL):**
    ```json
    {
      "verificationResult": "PARTIAL",
      "lastLocationTime": "2025-02-11T08:00:41.665176Z",
      "matchRate": 67
    }
    ```
    (Source: https://developer.networkascode.nokia.io/docs/location/location-api, https://developer.networkascode.nokia.io/docs/location/location-verification)

By understanding these fields and their possible values, you can effectively interpret the Network Insights API responses and integrate them into your applications to make informed decisions based on real-time network performance and device location data.

Question: What do I need to do to my application in order to be able to receive notifications from Network as Code?

Response:

To receive notifications from Nokia Network-as-Code (NaC), you need to configure your application to act as a webhook receiver. This involves setting up an HTTP endpoint (a "notification URL") that NaC can send `POST` requests to, along with an optional authentication token for security.

Here's what you need to do:

1.  **Set up a Notification URL (Webhook Endpoint):**
    Your application needs to expose an HTTP endpoint that can listen for incoming `POST` requests. This endpoint will be the `notification_url` you provide when subscribing to events in NaC. The exact implementation can be handled by developers as they see fit.

    **Example (Python using FastAPI):**
    ```python
    from fastapi import FastAPI, Header
    from pydantic import BaseModel
    from typing import Union, Annotated

    app = FastAPI()

    # Define the structure of the incoming notification
    class Data(BaseModel):
        # Example data structure, this will vary based on notification type
        device: dict | None = None
        subscriptionId: str | None = None
        roaming: dict | None = None # For roaming notifications
        # ... other fields depending on the notification type

    class Notification(BaseModel):
        id: str
        source: str
        type: str
        specversion: str
        datacontenttype: str
        time: str
        data: Data # The actual payload of the notification

    @app.post("/notifications")
    def receive_notification(
        notification: Notification,
        authorization: Annotated[Union[str, None], Header()] = None
    ):
        # Validate the authorization token if one is expected
        if authorization == "Bearer my-token": # Replace "my-token" with your actual token
            # Process the incoming notification
            print("Received notification:")
            print(notification)
            # You can now react to the notifications based on the Notification object
            return {"status": "Notification received and processed"}
        else:
            # Handle unauthorized access
            print("Unauthorized notification attempt.")
            return {"status": "Unauthorized"}, 401

    # To run this: save as, e.g., `main.py` and run `uvicorn main:app --reload`
    ```

    **Example (TypeScript using Express.js):**
    ```typescript
    import express, { Express, Request, Response } from "express";

    const app: Express = express();
    const port = process.env.PORT || 3000;

    app.use(express.json()); // Middleware to parse JSON request bodies

    // Define the structure of the incoming notification (example for device status)

        id: string;
        source: string;
        type: string;
        specversion: string;
        datacontenttype: string;
        time: string;
        data: {
            device: {
                phoneNumber?: string;
                networkAccessIdentifier?: string;
                ipv4Address?: {
                    publicAddress?: string;
                    privateAddress?: string;
                    publicPort?: number;
                };
                ipv6Address?: string;
            };
            subscriptionId: string;
            terminationReason?: string;
        };
    }

    app.post("/notifications", (req: Request, res: Response) => {
        // Check for authorization header if you've configured one
        const authorizationHeader = req.headers.authorization;
        if (authorizationHeader === "Bearer my-token") { // Replace "my-token"
            const notification: DeviceStatusNotification = req.body;
            // We can now use the notification object to react to changes
            console.log("Received notification:", notification);
            res.status(200).end(); // Acknowledge receipt
        } else {
            console.log("Unauthorized notification attempt.");
            res.status(401).send("Unauthorized");
        }
    });

    app.listen(port, () => {
        console.log(`[server]: Server is running at http://localhost:${port}`);
    });
    ```

Question: How do I interpret the network insights API response?

Response:

The Nokia Network-as-Code (NaC) Network Insights API provides valuable data about network conditions and device states. Interpreting the responses from these APIs depends on the specific insight you are querying, such as congestion levels or device location verification.

Here's how to interpret responses from key Network Insights functionalities:

### 1. Congestion Levels API Response

The Congestion Levels API allows you to poll for current, historical, or predictive congestion data for a device.

**a. Polling Current Congestion Levels:**
When you poll for the current congestion level, the API returns an array of congestion level objects.
*   **`level`**: This is the primary indicator, which can be one of the following string values:
    *   `"None"`: No congestion detected.
    *   `"Low"`: Low level of network congestion.
    *   `"Medium"`: Medium level of network congestion.
    *   `"High"`: High level of network congestion.

    **Example Output (Python):**
    ```
    High
    ```
    (Source: https://developer.networkascode.nokia.io/docs/network-insights/congestion-levels)

**b. Getting Predictions or Historical Data:**
When requesting congestion data between two timestamps, the API returns an array of `Congestion` objects, each providing a specific time window and a confidence level for predictions.
*   **`start`**: An ISO 8601 formatted date string indicating the beginning of the time period for which the congestion level applies.
*   **`end`**: An ISO 8601 formatted date string indicating the end of the time period for which the congestion level applies.
*   **`level`**: The predicted or historical congestion level for that period, using the same values as above (`"None"`, `"Low"`, `"Medium"`, `"High"`).
*   **`confidence`**: A numeric value from 0 to 100, representing the percentage confidence in the prediction. This is particularly useful for predictive data.

    **Example Output (Python for prediction):**
    ```
    2024-09-09T11:09:52.950638
    2024-09-09T11:11:30.950638
    High
    75
    ```
    This indicates that between the `start` and `end` timestamps, the congestion level is predicted to be "High" with a 75% confidence.
    (Source: https://developer.networkascode.nokia.io/docs/network-insights/congestion-levels)

**c. Congestion Notification Details (Webhook Payload):**
If you subscribe to congestion notifications, your configured `notificationUrl` will receive `JSON` objects with the following structure:
*   **`id`**: A string value representing the event subscription identifier.
*   **`source`**: A string identifying the source of the event, including the NaC API implementation and subscription ID.
*   **`type`**: A string value returned by the API with different statuses (e.g., "event").
*   **`specversion`**: A string representing the specification version.
*   **`datacontenttype`**: Indicates the media type for the event payload encoding, typically "application/json".
*   **`time`**: An ISO 8601 formatted date string indicating when the event occurred.
*   **`data`**: An object containing the actual congestion level data.
    *   **`data.level`**: The congestion level, which can be `"none"`, `"low"`, `"medium"`, or `"high"`.

    **Example JSON Schema for Congestion Notification:**
    ```json
    {
      "id": "2628b42e87894fcd942a841f16f52897",
      "source": "org.camaraproject.congestioninsights.v0.event",
      "type": "event",
      "specversion": "1.0",
      "datacontenttype": "application/json",
      "time": "2025-04-18T12:54:21.495311",
      "data": {
        "level": "Medium"
      }
    }
    ```
    (Source: https://developer.networkascode.nokia.io/docs/network-insights/congestion-schema)

### 2. Location API Response (Verifying Device Location)

The `POST verifyLocation` endpoint returns a `JSON` object that indicates whether a device is within a specified geographical area.
*   **`verificationResult`**: This is the primary result, indicating the device's location status relative to the defined area. It can be:
    *   `"TRUE"`: The device is within the circle defined by its center location and radius.
    *   `"FALSE"`: The device is outside the defined circle.
    *   `"PARTIAL"`: The device's location partially overlaps with the defined circle. In this case, `matchRate` will also be included.
    *   `"UNKNOWN"`: No historical location data is available for the device. In this case, `lastLocationTime` will not be provided.
*   **`lastLocationTime`**: An ISO 8601 formatted date-time string indicating the timestamp of the last known location information for the device. This is not provided if `verificationResult` is `"UNKNOWN"`.
*   **`matchRate`**: An integer value (1-99) included *only* when `verificationResult` is `"PARTIAL"`. It estimates the percentage match between the requested area and the area where the network locates the device. It's calculated as `(R ∩ N) / N * 100`, where R is the requested area and N is the network-located area.

    **Example Response (TRUE):**
    ```json
    {
      "verificationResult": "TRUE",
      "lastLocationTime": "2025-02-11T08:00:41.665176Z"
    }
    ```
    **Example Response (PARTIAL):**
    ```json
    {
      "verificationResult": "PARTIAL",
      "lastLocationTime": "2025-02-11T08:00:41.665176Z",
      "matchRate": 67
    }
    ```
    (Source: https://developer.networkascode.nokia.io/docs/location/location-api, https://developer.networkascode.nokia.io/docs/location/location-verification)

By understanding these fields and their possible values, you can effectively interpret the Network Insights API responses and integrate them into your applications to make informed decisions based on real-time network performance and device location data.

Question: What is the difference between network APIs and regular APIs?

Response:

The distinction between "network APIs" and "regular APIs" lies primarily in what they expose and control.

### Regular APIs (General APIs)

**What they are:**
"Regular APIs" (Application Programming Interfaces) are broad terms for interfaces that allow different software components to communicate and exchange data. They are the backbone of modern software development, enabling applications to integrate with various services, databases, and other applications.

**Examples:**
*   **Social Media APIs:** Allow applications to post updates, retrieve user data, or integrate login functionality (e.g., Twitter API, Facebook Graph API).
*   **Payment Gateway APIs:** Enable applications to process transactions securely (e.g., Stripe API, PayPal API).
*   **Cloud Service APIs:** Provide programmatic access to cloud computing resources like storage, virtual machines, or machine learning services (e.g., AWS S3 API, Google Cloud Vision API).
*   **Mapping APIs:** Allow applications to embed maps, get directions, or search for locations (e.g., Google Maps API).

**Focus:**
Their primary focus is on application logic, data exchange, and service invocation within a specific application domain. They abstract the complexity of the service they provide.

### Network APIs (in the context of Nokia Network-as-Code)

**What they are:**
Network APIs are a specialized type of API that specifically expose and allow programmatic control over the underlying capabilities and resources of a telecommunications network (like 4G, 5G, or fixed networks). They transform the network from a static "black box" into a programmable asset.

**Examples (from Nokia NaC):**
*   **Quality of Service on Demand (QoD) API:** Allows an application to dynamically request guaranteed bandwidth or low latency for a specific device or data flow for a certain duration.
*   **Device Location API:** Enables applications to verify a device's geographic location or retrieve its coordinates.
*   **Network Slicing API:** Allows developers to create, manage, and attach devices to specialized network slices, tailoring network performance (e.g., bandwidth, latency, security) to specific application needs.
*   **Congestion Insights API:** Provides information about network congestion levels (current, historical, or predictive) for a given area or device.
*   **SIM Swap API:** Helps detect potential fraud by checking if a device's SIM card has recently been swapped.

**Focus:**
Their primary focus is on exposing and controlling network-level capabilities, conditions, and resources. They abstract the immense complexity of telecom infrastructure, making network programming accessible to application developers who may not have deep telecom expertise.

### Key Differences Summarized:

| Feature             | Regular APIs                                     | Network APIs (Nokia NaC)                               |
| :------------------ | :----------------------------------------------- | :----------------------------------------------------- |
| **Core Function**   | Expose application logic, data, or general services. | Expose and control underlying network capabilities.    |
| **What they affect** | Application behavior, data flow, service integration. | Network behavior (QoS, routing, resource allocation).  |
| **Underlying Tech** | Databases, web servers, cloud services, specific application logic. | 5G Core, Radio Access Network, network infrastructure. |
| **Capabilities**    | Get user profile, process payment, send email, map data. | Guarantee QoS, verify device location, create network slice, check congestion. |
| **Complexity**      | Abstracts application-level complexity.           | Abstracts deep telecom and network infrastructure complexity. |
| **Goal**            | Enable integration, add features, exchange data. | Enable network-aware applications, optimize network usage, create new network-driven services. |
| **Target User**     | General software developers.                     | Application developers, enterprise developers (often without telecom background). |

In essence, while both are APIs that facilitate communication between software components, **Network APIs** are distinguished by their direct interaction with and control over the telecommunications network itself, enabling applications to become "network-aware" and dynamically adapt to or request specific network conditions.

Question: What is the difference between network APIs and regular APIs?

Response:

The distinction between "network APIs" and "regular APIs" lies primarily in what they expose and control.

### Regular APIs (General Software APIs)

"Regular APIs" (Application Programming Interfaces) are a broad category that encompasses most APIs you encounter in software development. They are designed to allow different software applications or components to communicate and interact with each other.

*   **What they expose:** Functionalities, data, or services of a specific software application, platform, or system.
*   **Examples:**
    *   A **payment gateway API** (e.g., Stripe, PayPal) allows an e-commerce site to process payments.
    *   A **social media API** (e.g., Twitter, Facebook) allows applications to post updates or retrieve user data.
    *   A **mapping API** (e.g., Google Maps) allows applications to embed maps and location services.
    *   An **internal microservice API** allows different parts of a larger software system to exchange data.
*   **Focus:** Application-level logic, data management, user interaction, and specific software features. They operate *over* the network, using standard internet protocols (like HTTP/HTTPS), but they don't typically control the network itself.

### Network APIs (in the context of Nokia Network-as-Code)

Network APIs are a specialized type of API that directly expose and allow programmatic control over the underlying capabilities and resources of a telecommunications network, particularly 5G networks. Nokia Network-as-Code (NaC) is specifically designed to make these powerful network functionalities accessible to developers.

*   **What they expose:** Core network functions, radio access network (RAN) capabilities, and network intelligence.
*   **Examples (from Nokia NaC):**
    *   **Quality of Service (QoS) on Demand API:** Allows an application to request a temporary boost in bandwidth or a guarantee of low latency for a specific device or session.
    *   **Network Slicing API:** Enables applications to create, manage, and attach devices to dedicated, customized "slices" of the network with specific performance characteristics.
    *   **Device Location API:** Provides precise geographic coordinates or verifies the location of a device.
    *   **Device Status API:** Checks if a device is connected to the network or if it's roaming.
    *   **SIM Swap API:** Detects if a device's SIM card has recently been changed, useful for fraud prevention.
*   **Focus:** Programming the network itself to adapt its behavior and resources to the specific needs of an application or user. They turn the network from a static "black box" into a dynamic, programmable platform.

### Key Differences Summarized

| Feature             | Regular APIs                                     | Network APIs (Nokia NaC)                               |
| :------------------ | :----------------------------------------------- | :----------------------------------------------------- |
| **Core Function**   | Expose application/service functionalities.      | Expose and control underlying network capabilities.    |
| **Domain**          | Application layer, software services.            | Network infrastructure, telecom services (e.g., 5G).   |
| **Control Level**   | Interact with software logic and data.           | Program the network's behavior, resources, and QoS.    |
| **Impact**          | Affect application features and data flow.       | Directly influence network performance, security, and resource allocation for an application. |
| **Complexity**      | Abstracts application-specific complexity.        | Abstracts complex telecom network engineering.          |
| **Use Cases**       | E-commerce, social media integration, data analytics, internal system integration. | Dynamic QoS for gaming/VR, network slicing for enterprises, fraud prevention, device tracking, IoT connectivity. |

In essence, while both types of APIs facilitate communication between software components, Network APIs provide a unique capability: they allow applications to directly influence and adapt the network's behavior to meet their specific requirements, leading to more intelligent, responsive, and optimized user experiences.
