Question: How does network as code handle end-user consent?

Response:

Nokia Network-as-Code (NaC) adopts a privacy-by-design approach to handle end-user consent, ensuring compliance with data protection regulations like GDPR. Consent management is crucial for granting or revoking an application's access to APIs and their parameters, allowing authorized devices to be used safely.

Here's how NaC handles end-user consent:

1.  **Purpose of Consent:** Applications often need to process personal or private enterprise information (e.g., location data, phone number information, mobile subscription details). To do this with "legitimate interest" and a legal basis, consent (authorization) from device owners is required.

2.  **Consent Terminology:**
    *   **Scope:** Defines the authorized feature or operation, typically by API name (e.g., "Location Verification," "Quality-of-service on Demand sessions"). It can be extended with specific resources or actions like "read" or "write."
    *   **Device ID:** The identifier for the device or subscriber, such as a phone number or an email-like identifier.
    *   **Authorized Party:** The private enterprise or organization authorized to use devices within defined scopes.
    *   **Operator:** The owner of the network accessible through NaC APIs.

3.  **B2B Consent Scenario:**
    *   For Business-to-Business scenarios, an **Organization Admin** submits an authorization request to the Network as Code support team.
    *   This involves filling out a specific Consent & Authorization template, detailing:
        *   Legal names of the authorizing and authorized organizations.
        *   Date of consent.
        *   Device IDs (phone numbers or external identifiers).
        *   Specific API scopes being authorized.
        *   The authorized party's organization name (as listed in the NaC Dashboard).
        *   The operator name.
        *   A revocation date for each consent.
    *   NaC support validates this information with the operators to enable access. Submitting a new request completely revokes previous authorizations for devices not included in the new list.

4.  **Application Registration and Consent Screenshots:**
    *   During the application registration process, developers must submit information about their business and the network capabilities they intend to use.
    *   Crucially, applications are expected to ask for end-user consent for actions involving personal information. Developers must provide screenshots of each step in their application's consent request flow, compiled into a PDF document. These screenshots are submitted to network operators to validate compliance with data privacy legislation.

5.  **End-User Consent Flows (Client-Initiated):**
    *   **Client Initiated Backchannel Authentication (CIBA) flow:** In simpler cases, NaC handles end-user requests using CIBA. NaC polls an Authorization Server, which triggers an end-user consent request. Once approved, the Authorization Server provides a client token. From the developer's perspective, this flow is largely transparent, with NaC handling the polling for access tokens.
    *   **Authorization Code flow:** If the end-user needs to take positive action to indicate consent, this flow is used. The application developer constructs an authorization URL pointing to the NaC authorization server, including their redirect handler. The end-user is directed to this URL, then to their operator-specific consent portal. If consent is given, the user is redirected back to the application's redirect URI with an operator code, which is then exchanged for a single-use access token.

6.  **Dynamic Purpose Specification:**
    *   For some APIs, a valid purpose for the authorization request must be specified (e.g., `dpv:FraudPreventionAndDetection` for fraud detection). This purpose can be associated with a scope (e.g., `dpv:FraudPreventionAndDetection number-verification:verify`).
    *   For APIs other than Number Verification, NaC automatically supplies the purpose specified during application registration and API plan subscription. If a new purpose arises, developers must notify NaC support to update their application's API call purpose information.

7.  **Number Verification Specifics:**
    *   The Number Verification API uses a 3-legged OAuth 2.0 flow, where a network subscriber provides consent through a Network Provider interface. A mobile app initiates verification by requesting an authorization URL, which the end-user must access via a mobile connection to provide consent. The NaC SDKs simplify this process by automatically issuing intermediate requests.

*   Source: https://developer.networkascode.nokia.io/docs/general-concepts/consent-identity-mgmt

Question: What do I need to do to my application in order to be able to receive notifications from Network as Code?

Response:

To enable your application to receive notifications from Nokia Network-as-Code (NaC), you need to configure a notification URL (also known as a callback URL or webhook) and set up an HTTP server within your application to handle incoming POST requests.

Here's a breakdown of what's required:

1.  **Create an API Endpoint (Notification URL):**
    *   You must create or provide an API endpoint within your application that NaC can send notifications to. This endpoint acts as a webhook.
    *   It needs to be a **web server** configured to receive `POST` requests. These requests will contain session-related updates, such as session creation, deletion, duration, or device status changes.

2.  **Implement a Notification Handler:**
    *   Your application's HTTP server needs a specific endpoint (e.g., `/notifications` or `/device-status`) to listen for these `POST` requests.
    *   The incoming `POST` request will contain the notification payload, typically in JSON format, and an `Authorization: Bearer <token>` header.
    *   You will need to parse this payload and react to the notifications based on the event details.

3.  **Provide a Notification Authentication Token:**
    *   A `notification_auth_token` (or `notificationAuthToken` in TypeScript) is a password used to identify the sender of the notification.
    *   You specify this token when subscribing to events in NaC. NaC will then include this token in the `Authorization` header of the `POST` requests it sends to your `notification_url`.
    *   Your notification handler should verify this token to ensure the notification originates from NaC.

4.  **Subscription Parameters:**
    *   When you subscribe to a specific event type (e.g., `CONNECTIVITY`, `ROAMING_STATUS`, geofencing events, slice notifications), you will include the `notification_url` and `notification_auth_token` as parameters in your subscription request.
    *   Other parameters like `event_type`, `device` ID, and `max_num_of_reports` (for some event types) are also part of the subscription.

**Example of a conceptual notification handler (Python using FastAPI):**

```python
from fastapi import FastAPI, Header
from pydantic import BaseModel
from typing_extensions import Annotated
from typing import Union, Optional

app = FastAPI()

# Define Pydantic models for the expected notification structure
# (This structure varies depending on the event type, e.g., Connectivity, Roaming, Slice)
class Device(BaseModel):
    phoneNumber: Optional[str] | None
    networkAccessIdentifier: Optional[str] | None
    ipv4Address: Optional[str] | None
    ipv6Address: Optional[str] | None

class ConnectivityEventDetail(BaseModel):
    device: Device
    subscriptionId: str
    deviceStatus: str
    terminationReason: str

class Event(BaseModel):
    eventType: str
    eventTime: str
    eventDetail: ConnectivityEventDetail

class Notification(BaseModel):
    id: str
    source: str
    type: str
    specversion: str
    datacontenttype: str
    time: str
    data: Event # Or Data, depending on the notification type

@app.post("/notifications")
def receive_notification(
    notification: Notification,
    authorization: Annotated[Union[str, None], Header]
):
    # Verify the authentication token
    if authorization == "Bearer my-token": # Replace "my-token" with your actual notification_auth_token
        # Process the notification
        print(f"Received notification: {notification.type}")
        print(f"Event details: {notification.data.eventDetail}")
        # Implement your application logic here based on the notification content
        return {"message": "Notification received successfully"}
    else:
        return {"message": "Unauthorized"}, 401

# To run this example: uvicorn your_module_name:app --port 8000
```

By setting up such an endpoint and providing the necessary `notification_url` and `notification_auth_token` during subscription, your application will be able to receive real-time updates from various NaC functionalities, including device connectivity status, roaming status, QoD sessions, slice lifecycle events, geofencing alerts, and more.

Question: What is a code example that uses QoD API?

Response:

Here is a code example demonstrating how to create a Quality-of-service on Demand (QoD) session using the Nokia Network-as-Code (NaC) Python SDK. This example sets up a QoD session with a large bandwidth profile for a specified duration between a device and an application server.

```python
import network_as_code as nac
from network_as_code.models.device import DeviceIpv4Addr

# 1. Begin by creating a Network as Code client
# Replace "<your-application-key-here>" with your actual application key from the NaC Dashboard.
client = nac.NetworkAsCodeClient(
    token="<your-application-key-here>"
)

# 2. Identify the mobile network device
# Devices can be identified by phone number, IPv4 address (public/private/port), or IPv6 address.
# For test devices, use specific prefixes like "+3672" for phone numbers.
my_device = client.devices.get(
    ipv4_address=DeviceIpv4Addr(
        public_address="233.252.0.2",
        private_address="192.0.2.25",
        public_port=80
    ),
    # The phone number does not accept spaces or parentheses
    phone_number="+36721601234567"
)

# 3. Create a QoD session for the device
# This instructs Network as Code to set up a QoD session between the device and the specified service.
# 'profile': "DOWNLINK_L_UPLINK_L" ensures maximum bandwidth.
# 'duration': 3600 seconds (1 hour).
my_session = my_device.create_qod_session(
    service_ipv4="233.252.0.2",
    service_ipv6="2001:db8:1234:5678:9abc:def0:fedc:ba98",
    profile="DOWNLINK_L_UPLINK_L",
    duration=3600
)

# 4. Confirm that the device has the newly created session
print("QoD sessions for the device:")
print(my_device.sessions())

# 5. Optionally, clear out all sessions for the device to avoid unexpected costs
# my_device.clear_sessions()
```

This example demonstrates the following:
*   **Client Initialization:** Establishing a connection to the Network as Code platform using your application key.
*   **Device Identification:** Specifying the target mobile device using its IPv4 address details and phone number.
*   **Session Creation:** Calling `create_qod_session` on the device object, providing the application server's IP addresses, a Quality of Service profile (`DOWNLINK_L_UPLINK_L` for large bandwidth), and the session duration.
*   **Session Verification:** Using `my_device.sessions()` to retrieve and print a list of all active QoD sessions associated with the device.

Question: How do I interpret the network insights API response?

Response:

Interpreting the Nokia Network-as-Code (NaC) Network Insights API response, particularly for congestion, involves understanding the structure and meaning of the returned JSON objects. The responses typically provide details about congestion levels, timestamps, and confidence in predictions.

Here's how to interpret key elements of a Network Insights (Congestion) API response:

### Common Fields in Congestion Notifications and Polling Responses

Whether you are receiving a congestion notification via a webhook or polling for congestion levels, the JSON response will contain several standard fields:

*   **`id`**: A string value representing the event or subscription identifier.
*   **`source`**: A string indicating the origin of the event, often identifying the NaC API implementation and subscription ID (e.g., `"org.camaraproject.congestioninsights.v0.event"`).
*   **`type`**: A string value returned by the API with different statuses (e.g., `"event"`).
*   **`specversion`**: A string indicating the specification version (e.g., `"1.0"`).
*   **`datacontenttype`**: Specifies the media type for the event payload encoding, which is typically `"application/json"` for CAMARA APIs.
*   **`time`**: A string value indicating when the event occurred, formatted according to ISO 8601 (e.g., `"2025-04-18T12:54:21.495311"`).
*   **`data`**: An object that contains the specific congestion level data.

### Congestion-Specific Data (`data` object)

Within the `data` object, you will find the core information about network congestion:

*   **`level`**: A string specifying the congestion level experienced by the device. Possible values include:
    *   `"None"`
    *   `"Low"`
    *   `"Medium"`
    *   `"High"`
    This indicates the current or predicted state of network congestion.
*   **`start`**: (For predictions/historical data) A timestamp (ISO 8601 formatted string) indicating the beginning of the period for which the congestion data is valid.
*   **`end`**: (For predictions/historical data) A timestamp (ISO 8601 formatted string) indicating the end of the period for which the congestion data is valid.
*   **`confidence`**: (For predictions) A numeric value ranging from 0 to 100, representing the percentage confidence in the congestion prediction. A higher value indicates greater certainty in the predicted congestion level.

### Example Interpretation

Consider a response for a congestion prediction:

```json
{
  "id": "2628b42e-8789-4fcd-942a-841f16f52897",
  "source": "org.camaraproject.congestioninsights.v0.event",
  "type": "event",
  "specversion": "1.0",
  "datacontenttype": "application/json",
  "time": "2025-04-18T12:54:21.495311",
  "data": {
    "level": "Medium",
    "start": "2024-09-09T11:09:52.950638Z",
    "end": "2024-09-09T11:11:30.950638Z",
    "confidence": 75
  }
}
```

This response indicates:
*   The event occurred at `2025-04-18T12:54:21.495311`.
*   For the period between `2024-09-09T11:09:52.950638Z` and `2024-09-09T11:11:30.950638Z`, the network is predicted to experience a **"Medium"** congestion level.
*   There is a **75%** confidence in this prediction.

By understanding these fields, applications can react proactively to network conditions, such as adjusting data rates, offloading traffic, or informing users about potential performance impacts.

Question: What do I need to do to my application in order to be able to receive notifications from Network as Code?

Response:

To receive notifications from Nokia Network-as-Code (NaC), your application needs to be configured to act as a **notification handler** or **webhook endpoint**. This involves setting up an HTTP server that can receive `POST` requests from the NaC backend.

Here's what you need to do:

1.  **Create an API Endpoint (Callback URL/Webhook):**
    *   Your application must expose an HTTP endpoint (a URL) that NaC can send notifications to. This is often referred to as a callback URL or webhook.
    *   This endpoint needs to be a **web server** configured to receive `POST` requests.
    *   The incoming `POST` requests will contain session-related updates, such as session creation, deletion, duration, device status changes, geofencing events, or slice state transitions.

2.  **Implement a Notification Handler:**
    *   Within your application, you'll write code to process the incoming `POST` requests at this endpoint.
    *   Notifications are typically sent as JSON payloads. For example, geofencing notifications are delivered using [CloudEvents](https://cloudevents.io/).
    *   The handler should parse the JSON body of the request to extract the notification details.

3.  **Provide a Notification Authentication Token:**
    *   When you subscribe to notifications (e.g., for device connectivity, roaming status, geofencing, or network slicing), you must specify a `notification_auth_token`.
    *   This token is a password used to identify the sender of the notification.
    *   The NaC backend will include this token in the `Authorization: Bearer <token>` header of the `POST` request sent to your `notification_url`. Your application's handler should validate this token to ensure the notification is legitimate and from NaC.

4.  **Use HTTPS for Security:**
    *   It is highly recommended to use HTTPS for your `notification_url` to ensure secure communication and protect the integrity and confidentiality of the notifications.

**Example of a Python Notification Handler (using FastAPI):**

```python
# status_handler.py for CONNECTIVITY
# run with: uvicorn status_handler:app

from pydantic import BaseModel
from typing_extensions import Annotated
from typing import Union, Optional

app = FastAPI()

class Device(BaseModel):

    ipv4Address: Optional[str] | None
    ipv6Address: Optional[str] | None

class ConnectivityEventDetail(BaseModel):
    device: Device
    subscriptionId: str
    deviceStatus: str
    terminationReason: str

class Event(BaseModel):
    eventType: str
    eventTime: str
    eventDetail: ConnectivityEventDetail

class Notification(BaseModel):
    id: str
    source: str
    type: str
    specversion: str
    datacontenttype: str
    time: str
    data: Event # Note: The source shows 'data: Data' but the example uses 'Event' for connectivity.

@app.post("/notifications")
def receive_notification(
    notification: Notification,
    authorization: Annotated[Union[str, None], Header]
):
    # Validate the authorization token
    if authorization == "Bearer my-token": # Replace "my-token" with your actual notification_auth_token
        # Process the notification based on its content
        print(f"Received notification: {notification.eventDetail.deviceStatus} for device {notification.eventDetail.device.phoneNumber}")
        # Your application logic here (e.g., update a database, trigger another action)
    else:
        print("Unauthorized notification received.")
    return {"status": "Notification received"}
```

        client = nac.NetworkAsCodeClient(token=app_key)
        print("NaC client initialized successfully.")
    except Exception as e:
        print(f"Error initializing NaC client: {e}")

        private_address="192.0.2.25",
        public_port=80
    )

    test_phone_number = "+36721601234567" # Simulator phone number prefix +3672

        my_device = client.devices.get(
            ipv4_address=test_device_ipv4,
            ipv6_address=test_device_ipv6,
            phone_number=test_phone_number
        )
        print(f"Device identified: {my_device.phone_number}")
    except Exception as e:
        print(f"Error identifying device: {e}")
        return

    # This instructs the network to prioritize traffic between the device
    # and the specified application server for a given duration.
    # 'DOWNLINK_L_UPLINK_L' is an example QoS profile for large bandwidth.
    # The duration is mandatory and specified in seconds (e.g., 3600 seconds = 1 hour).
    application_server_ipv4 = "233.252.0.2"
    application_server_ipv6 = "2001:db8:1234:5678:9abc:def0:fedc:ba98"
    session_duration_seconds = 3600 # 1 hour

    try:
        print(f"\nCreating a QoD session for device {my_device.phone_number}...")
        my_session = my_device.create_qod_session(
            service_ipv4=application_server_ipv4,
            service_ipv6=application_server_ipv6,
            profile="DOWNLINK_L_UPLINK_L",
            duration=session_duration_seconds
        )
        print(f"QoD session created successfully with ID: {my_session.id}")
        print(f"QoS Profile: {my_session.profile}")
        print(f"Session duration: {my_session.duration()} seconds")
        print(f"Session started at: {my_session.startedAt}")
        print(f"Session expires at: {my_session.expiresAt}")

    except Exception as e:
        print(f"Error creating QoD session: {e}")
        # Attempt to clear sessions even if creation failed, in case a partial session was made
        my_device.clear_sessions()
        return

    # 4. List all QoD sessions associated with the device
    # A device can have multiple sessions programmed for it.
    print(f"\nListing all QoD sessions for device {my_device.phone_number}:")
    try:
        all_sessions = my_device.sessions()
        if all_sessions:
            for session in all_sessions:
                print(f"  - Session ID: {session.id}, Profile: {session.profile}, Status: {session.qosStatus}")
        else:
            print("  No sessions found for this device.")
    except Exception as e:
        print(f"Error listing sessions: {e}")

    # 5. (Optional) Retrieve a specific session by its ID
    try:
        print(f"\nRetrieving specific session by ID: {my_session.id}")
        retrieved_session = client.sessions.get(my_session.id)
        print(f"  Retrieved Session ID: {retrieved_session.id}, Status: {retrieved_session.qosStatus}")
    except Exception as e:
        print(f"Error retrieving specific session: {e}")

    # 6. Clear all QoD sessions for the device
    # It's important to clear sessions to avoid unexpected costs or resource usage.
    print(f"\nClearing all QoD sessions for device {my_device.phone_number}...")
    try:
        my_device.clear_sessions()
        print("All sessions cleared successfully.")
    except Exception as e:
        print(f"Error clearing sessions: {e}")

    print("\n--- QoD API Demonstration Complete ---")

Question: How do I interpret the network insights API response?

Response:

The Nokia Network-as-Code (NaC) Network Insights API primarily provides information related to **Congestion**. Interpreting the API response involves understanding the structure of the JSON objects returned, particularly for congestion notifications and congestion level polling or predictions.

Here's how to interpret the Network Insights API responses:

### 1. Congestion Notification Details

When you subscribe to congestion notifications, the API sends a JSON object to your specified `notificationUrl`. This object provides details about changes in congestion levels.

**Key fields in a Congestion Notification JSON schema:**

*   **`id`**: A string value representing the unique identifier of the event subscription.
*   **`source`**: A string value that identifies the origin of the event, including the Network as Code API implementation and the subscription ID (e.g., `"org.camaraproject.congestioninsights.v0.event"`).
*   **`type`**: A string value returned by the API indicating the event type, often `"event"`.
*   **`specversion`**: A string representing the specification version of the event.
*   **`datacontenttype`**: Indicates the media type for the event payload encoding, which is `"application/json"` for CAMARA APIs.
*   **`time`**: A string value with the timestamp when the event occurred, formatted according to ISO 8601 (e.g., `"2025-04-18T12:54:21.495311"`).
*   **`data`**: An object that contains the actual congestion level data.
    *   **`level`**: A string specifying the congestion level, which can be one of: `"none"`, `"low"`, `"medium"`, or `"high"`.

**Example Interpretation:**
If you receive a notification with `"level": "High"`, it means the network is experiencing significant congestion for the device associated with that subscription at the `time` indicated.

### 2. Congestion Level Polling and Prediction Data

When you poll for current, historical, or predictive congestion data, the API returns an array of congestion level objects.

**Key fields in Congestion Level Polling/Prediction responses:**

*   **`start`**: The start timestamp for the period to which the congestion data applies. This is an ISO 8601 formatted date string.
*   **`end`**: The end timestamp for the period to which the congestion data applies. This is also an ISO 8601 formatted date string.
*   **`level`**: The congestion level experienced by the device during the `start` and `end` period, ranging from `"None"`, `"Low"`, `"Medium"`, and `"High"`.
*   **`confidence`**: A numeric value from 0 to 100, representing the percentage confidence in the prediction. This field is particularly relevant when requesting predictive data.

**Example Interpretation:**
If a response contains an object with `start: "2024-09-09T11:09:52.950638"`, `end: "2024-09-09T11:11:30.950638"`, `level: "High"`, and `confidence: 75`, it indicates that for that specific time window, the network experienced high congestion with a 75% confidence level in that prediction.

### 3. General HTTP Responses

Like all NaC APIs, Network Insights APIs will also return standard HTTP status codes:

*   **`200 OK`**: Indicates a successful request. The response body will contain the requested data (e.g., congestion levels or subscription details).
*   **`400 Bad Request`**: Signifies issues with the client request, such as invalid arguments or malformed JSON. The response body will typically include a `code` (e.g., `"INVALID_ARGUMENT"`) and a `message` explaining the error.
*   **`401 Unauthorized`**: Occurs when there's an authentication issue, such as a missing, invalid, or expired API key.
*   **`403 Forbidden`**: Indicates that the client does not have sufficient permissions to perform the action or access the data. This could mean your application key is not subscribed to the specific API.
*   **`404 Not Found`**: The requested resource (e.g., a specific subscription ID) does not exist.
*   **`500 Internal Server Error`**: A generic error indicating a problem on the API server's side.

By understanding these structures and keyword values, you can effectively interpret the data provided by the Nokia Network-as-Code Network Insights API to monitor and react to network congestion.

Question: What is the difference between network APIs and regular APIs?

Response:

The distinction between "network APIs" (specifically in the context of Nokia Network-as-Code) and "regular APIs" lies primarily in their domain of control, the underlying systems they expose, and the type of functionality they enable.

### Network APIs (Nokia Network-as-Code context)

Network APIs, as offered by Nokia Network-as-Code (NaC), are specialized Application Programming Interfaces that expose and abstract the complex capabilities of mobile network infrastructure (like 5G networks) to application developers. They allow applications to programmatically interact with, control, and gain insights from the network itself.

**Key characteristics of Network APIs:**

*   **Domain:** Directly interact with and control the underlying telecom network infrastructure (e.g., 5G core, radio access network).
*   **Abstraction:** Abstract complex network functions and protocols (like those enabled by NWDAF or NEF) into simple, developer-friendly API calls. This removes the need for developers to have deep telecom expertise.
*   **Functionality:** Enable applications to dynamically request, manage, and optimize network resources and behavior. Examples include:
    *   **Quality of Service (QoS) on Demand:** Dynamically allocating bandwidth or guaranteeing low latency for specific application traffic.
    *   **Network Slicing:** Creating and managing dedicated, customized virtual network slices with specific performance characteristics.
    *   **Device Location:** Verifying or retrieving the geographic location of a device.
    *   **Device Status:** Monitoring a device's connectivity (e.g., online/offline, roaming status).
    *   **Network Insights:** Obtaining real-time or predictive information about network conditions like congestion.
    *   **Identity & Security:** Such as SIM Swap detection or Number Verification for fraud prevention.
*   **Purpose:** To make networks programmable and application-aware, allowing applications to adapt to network conditions, optimize performance, and enable new network-centric use cases.

### Regular APIs (General Definition)

"Regular APIs" is a broad term referring to any Application Programming Interface that allows different software systems to communicate and exchange data or functionality. These APIs are ubiquitous across various domains, from web services to operating systems and software libraries.

**Key characteristics of Regular APIs:**

*   **Domain:** Can operate in any software domain, such as social media platforms, payment gateways, mapping services, operating systems, or internal enterprise applications.
*   **Abstraction:** Abstract the internal implementation details of a specific application, service, or software component, allowing other software to use its features without needing to understand its internal workings.
*   **Functionality:** Typically focus on data retrieval, data submission, triggering specific actions within an application, or integrating different software services. Examples include:
    *   A weather API providing current temperature data.
    *   A payment gateway API processing transactions.
    *   A social media API allowing posts to be published programmatically.
    *   A mapping API displaying geographical data or calculating routes.
*   **Purpose:** To facilitate software integration, enable data sharing, extend the functionality of existing applications, and build new applications on top of existing services.

### Key Differences Summarized

| Feature             | Network APIs (Nokia NaC)                               | Regular APIs (General)                                     |
| :------------------ | :----------------------------------------------------- | :--------------------------------------------------------- |
| **Primary Focus**   | Programmatic control and insights into the network     | Inter-application communication and data exchange          |
| **Underlying System** | Telecom network infrastructure (e.g., 5G core, RAN)    | Any software application, service, or database             |
| **Abstraction Layer** | Network complexities (e.g., 5G protocols, NEF, NWDAF) | Application/service internal logic and data structures     |
| **Capabilities**    | Dynamic QoS, network slicing, device location/status, congestion insights, fraud prevention via network data | Data retrieval, data submission, specific application actions, integration |
| **Goal**            | Network-aware applications, optimized network performance, new network-centric use cases | Software integration, functionality reuse, extending application features |

In essence, while both types of APIs enable software to interact with other systems, Network APIs specifically target and manipulate the network itself, providing a layer of programmability that traditional APIs do not.

Question: What do I need to do to my application in order to be able to receive notifications from Network as Code?

Response:

To receive notifications from Nokia Network-as-Code (NaC), your application needs to be configured with a specific endpoint that NaC can send updates to. This involves setting up a notification URL and handling the incoming requests.

Here's what you need to do:

1.  **Create an API Endpoint (Notification URL):**
    *   Your application must expose an HTTP endpoint (also known as a callback URL or webhook) that NaC can reach. This URL will be specified as the `notification_url` (or `sink` in some contexts like geofencing) when you subscribe to events.
    *   This endpoint needs to be a web server configured to receive `POST` requests. NaC will send session-related updates (e.g., session creation, deletion, duration, device status changes, slice state transitions) to this URL.

2.  **Implement a Notification Handler:**
    *   Within your application, you'll need code to process the incoming `POST` requests at your designated notification URL.
    *   The incoming requests will contain event information as a JSON payload. The structure of this payload will vary depending on the type of notification (e.g., device connectivity, roaming status, geofencing, slice notifications). For example, geofencing notifications are delivered using CloudEvents.

3.  **Provide an Authentication Token:**
    *   When subscribing to notifications, you must provide a `notification_auth_token` (or `notificationAuthToken` or `sink_credential`). This token acts as a password to identify the sender of the notification.
    *   NaC will include this token in the `Authorization: Bearer <token>` header of the `POST` request it sends to your `notification_url`. Your application's notification handler should validate this token to ensure the notification originated from NaC.

4.  **Subscribe to Events with the Notification URL and Token:**
    *   When you use NaC SDKs to subscribe to specific events (e.g., device connectivity status, geofencing events, slice notifications), you will pass your `notification_url` and `notification_auth_token` as parameters.

Question: What are network APIs and why should I use them?

Network APIs, within the context of Nokia Network-as-Code (NaC), are programmatic interfaces that expose the advanced capabilities of 5G networks to developers. Traditionally, networks have been complex and static, acting as "black boxes" to applications. NaC simplifies this by providing easy-to-use Software Development Kits (SDKs) and APIs that abstract away the underlying network complexity, making network programming accessible even without deep telecom experience.

You should use Nokia Network-as-Code APIs for several compelling reasons:

1.  **Simplified Network Programming:** NaC abstracts complex network functionalities into simple API calls and SDK methods. This allows developers to integrate network capabilities into their applications quickly and efficiently, without needing extensive knowledge of network infrastructure.
2.  **Dynamic Network Control and Programmability:** NaC enables applications to dynamically request and control network resources and capabilities on demand. This means your application can adapt to changing network conditions and specific requirements, making the network malleable to your application's needs.
3.  **Optimized Resource Utilization:** You can optimize network resources like bandwidth, latency, and connectivity for specific use cases. For example, you can prioritize data flows for critical applications, ensure guaranteed latency for VR/XR experiences, or boost bandwidth for streaming and gaming events.
4.  **Cost-Effectiveness:** By dynamically requesting network capabilities, applications can pay for premium network services only when they are actually used, rather than incurring constant high costs. This allows for optimized use of network capabilities at an optimized cost.
5.  **Enhanced Application Performance and User Experience:** Applications can become "network-aware," reacting to network conditions to maintain consistent performance. This leads to better, more innovative applications and a more reliable and consistent user experience.
6.  **Enabling New Use Cases and Innovation:** NaC unlocks a wide range of new possibilities for developers to create innovative, network-aware applications across various industries. Examples include:
    *   **Quality of Service on Demand (QoD):** Dynamically boost bandwidth for critical tasks or ensure low latency for real-time applications like gaming, AR/VR, or remote operations.

    *   **Network Insights:** Gain insights into network conditions, such as congestion levels or population density, to optimize application behavior (e.g., drone flight paths).
7.  **Modern Development Patterns:** NaC provides modern SDKs and API designs, making it easier for developers to integrate network functionalities into their existing development workflows.

In essence, Nokia Network-as-Code transforms networks from static infrastructure into programmable platforms, empowering developers to build more intelligent, responsive, and efficient applications that leverage the full potential of 5G.

Question: What is the difference between network APIs and regular APIs?

Response:

Network APIs, particularly in the context of Nokia Network-as-Code (NaC), differ from "regular" or general-purpose APIs primarily in their **domain of interaction** and the **type of capabilities they expose**.

Here's a breakdown of the differences:

1.  **Regular APIs (General-Purpose APIs):**
    *   **Domain:** These APIs typically expose functionalities related to specific applications, services, or data. They are designed for data exchange, integrating different software systems, or providing access to application-level business logic.
    *   **Examples:** APIs for social media platforms (e.g., posting updates, retrieving user data), payment gateways (e.g., processing transactions), mapping services (e.g., getting directions, location data), or e-commerce platforms (e.g., managing orders, product catalogs).
    *   **Focus:** Their primary concern is the interaction between software components, data manipulation, and service orchestration at the application layer.

2.  **Network APIs (Nokia Network-as-Code APIs):**
    *   **Domain:** These APIs specifically expose and allow programmatic control over the underlying network infrastructure, such as 5G mobile networks, private networks, and edge clouds.
    *   **Capabilities Exposed:** Instead of application data or business logic, Network APIs provide access to network-specific functionalities. These include:
        *   **Quality of Service (QoS) on Demand:** Dynamically allocating bandwidth, prioritizing traffic, or guaranteeing latency for specific applications or devices.
        *   **Device Insights:** Checking device connectivity status (online/offline, roaming), retrieving device location, or verifying phone numbers.
        *   **Specialized Networks (Network Slicing):** Creating, managing, and attaching devices to customized virtual network slices with tailored performance characteristics.
        *   **Network Insights:** Providing real-time analytics on network conditions like congestion levels or population density.
        *   **Identity & Security:** Features like SIM Swap detection for fraud prevention.
    *   **Abstraction:** Nokia NaC's core purpose is to abstract the inherent complexity of telecom networks, making these powerful network capabilities accessible to developers who may not have specialized telecom experience. It simplifies interaction with core network functions like the Network Exposure Function (NEF) and Network Data Analytics Function (NWDAF).
    *   **Impact:** The use of Network APIs directly impacts the performance, reliability, and behavior of network connectivity for applications and devices, rather than just the application's internal logic or data.

**In summary:**

While both types of APIs facilitate communication between software components, **regular APIs** focus on application-level services and data, whereas **Network APIs** (like those offered by Nokia NaC) provide a programmatic interface to *control and interact with the network itself*, enabling applications to become network-aware and dynamically adapt to network conditions.

The capabilities offered by Nokia Network-as-Code APIs, particularly **Quality of Service on Demand** and **Specialized Networks (Slicing)**, introduce mechanisms for differential treatment of network traffic.
