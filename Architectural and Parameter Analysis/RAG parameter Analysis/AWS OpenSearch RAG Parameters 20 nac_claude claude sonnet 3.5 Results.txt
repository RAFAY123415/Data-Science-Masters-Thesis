Question: Why do I need to include private, public IP addresses and port when creating a QoD session?

Response:

When creating a Quality-of-Service on Demand (QoD) session, you need to include private and public IP addresses along with the port for several important reasons:

1. Device Identification: 
   Devices cannot be uniquely identified by their public IPv4 address alone. The combination of public and private addresses, along with the port, provides a more precise way to identify the specific device for which you're creating the QoD session.

2. NAT Technology:
   Many mobile networks use Network Address Translation (NAT) technology. This means multiple devices can share the same public IP address. By providing both the public and private IP addresses, along with the port, you ensure the correct device behind the NAT is targeted for the QoD session.

3. Accurate Session Routing:
   The combination of these identifiers helps the network accurately route the QoD session to the intended device, ensuring that the quality of service improvements are applied to the correct connection.

4. Port Specification:
   Including the port allows for more granular control over which specific application or service on the device receives the QoD treatment. This is particularly useful when you want to prioritize traffic for a specific application.

5. Network Architecture Compatibility:
   This approach accommodates various network architectures and ensures compatibility across different types of mobile networks.

6. Security and Precision:
   By requiring this level of detail, it adds an extra layer of security and precision, preventing accidental application of QoD to unintended devices or services.

Here's an example of how you might specify these details when creating a QoD session:

```python
my_device = client.devices.get(
    ipv4_address=DeviceIpv4Addr(
        public_address="233.252.0.2",
        private_address="192.0.2.25",
        public_port=80
    ),
    ipv6_address="2001:db8:1234:5678:9abc:def0:fedc:ba98",
    phone_number="+36721601234567"
)
```

Remember, while providing all these details is ideal for precise control and optimal functionality, the QoD feature will still work even if you don't provide all the optional parameters like ports. The system is designed to be flexible while encouraging the most accurate device identification possible.

Question: How does network as code handle end-user consent?

Response:

Network as Code (NaC) handles end-user consent through two main flows: the Client Initiated Backchannel Authentication (CIBA) flow and the Authorization Code flow. Here's how each of these works:

1. Client Initiated Backchannel Authentication (CIBA) flow:

This is used in simpler cases and is largely transparent to the application developer.

- NaC handles requests for end-user consent by using CIBA.
- Access to the end-user device is guarded by an Authorization Server.
- NaC polls the Authorization Server until a response is provided.
- The Authorization Server triggers an appropriate end-user consent request which the user can approve or deny.
- When the request is approved, the Authorization Server provides a client token authorized to perform the desired action.
- From the application developer's perspective, this flow is essentially transparent. You just need to call the APIs normally with your application keys.
- NaC runtime takes care of polling for access tokens on behalf of the application.
- Note that this process may take some time, so you may need to adjust API request timeouts accordingly. NaC SDKs use extended timeouts by default.

2. Authorization Code flow:

This is used when an end user needs to take positive action to indicate their consent.

- The application developer constructs an authorization URL pointing to the NaC authorization server.
- This URL contains the developer's own redirect handler as a redirect URI.
- The end user application running on the end user device is directed to this URL.
- NaC then redirects the user to their operator-specific consent portal to approve the consent request.
- If consent is given, the application is redirected back to the application's redirect URI with an operator code.
- This code is then exchanged for a single-use access token.
- The access token is passed along with the subsequent request to an API, validating that the API is being called with user consent.

It's important to note that NaC adopts a privacy-by-design approach and complies with data protection regulations like GDPR. This means that a device's owner allows which applications or APIs can access their device. Consent management is about granting or revoking the access an application has to APIs and their parameters, ensuring authorized devices can be safely used.

For APIs other than Number Verification, NaC will automatically supply the purpose that was specified during application registration and API plan subscription. If your application uses API calls for a new purpose after registration, you need to notify NaC support to update your application's API call purpose information.

To receive notifications from Network as Code (NaC), you need to set up a notification handling system in your application. Here are the key steps and components you need to implement:

1. Set up a Notification URL (Webhook):
   You need to create an HTTP endpoint in your application that can receive POST requests. This endpoint will serve as your notification URL or webhook.

2. Implement a Notification Handler:
   Create a handler to process the incoming notifications. This typically involves setting up a web server with a POST endpoint.

3. Configure Authentication:
   Use a notification auth token to secure your endpoint. This token will be used to verify that the incoming notifications are legitimate.

4. Subscribe to Notifications:
   When creating sessions or using certain NaC features, you need to specify your notification URL and auth token.

Here's a basic example of how to set this up:

```python
from fastapi import FastAPI, Header
from pydantic import BaseModel
from typing_extensions import Annotated
from typing import Union

app = FastAPI()

class Notification(BaseModel):
    id: str
    source: str
    type: str
    specversion: str
    datacontenttype: str
    time: str
    data: dict  # The structure of 'data' will depend on the notification type

@app.post("/notifications")
def receive_notification(
    notification: Notification,
    authorization: Annotated[Union[str, None], Header()]
):
    if authorization == "Bearer my-token":
        # Process the notification
        print(notification)
    else:
        # Handle unauthorized requests
        pass
```

When using NaC features that support notifications, you'll need to include the notification URL and auth token. For example, when creating a QoD session:

```python
my_session = my_device.create_qod_session(

    duration=3600,
    notification_url="https://your-app.com/notifications",
    notification_auth_token="my-token"
)
```

Key points to remember:

- Always use HTTPS for your notification URL to ensure secure communication.
- The notification URL should be publicly accessible so that NaC can send notifications to it.
- The exact implementation of the notification handler can be customized based on your needs.
- Different NaC features may send different types of notifications, so your handler should be able to process various notification structures.
- Properly secure your endpoint to prevent unauthorized access or abuse.

   - Setting up a web server to listen for POST requests

When using NaC APIs, you need to specify the notification URL and an authentication token when subscribing to events.

```python
import network_as_code as nac
from network_as_code.models.device import Device, DeviceIpv4Addr

client = nac.NetworkAsCodeClient(token="<your-application-key-here>")

my_device = client.devices.get(
    "device@testcsp.net",
    ipv4_address=DeviceIpv4Addr(
        public_address="233.252.0.2",
        private_address="192.0.2.25",
        public_port=80
    ),
    phone_number="+36721601234567"
)

my_subscription = client.connectivity.subscribe(
    event_type="org.camaraproject.device-status.v0.connectivity-data",
    device=my_device,
    max_num_of_reports=5,
    notification_url="https://example.com/notify",
    notification_auth_token="replace-with-your-auth-token"
)
```

For handling notifications, you'll need to set up a web server. Here's a basic example using FastAPI:

```python
from fastapi import FastAPI, Header
from pydantic import BaseModel
from typing import Union, Optional

app = FastAPI()

class Notification(BaseModel):
    id: str
    source: str
    type: str
    specversion: str
    datacontenttype: str
    time: str
    data: dict

@app.post("/notifications")
def receive_notification(
    notification: Notification,
    authorization: Union[str, None] = Header(default=None)
):
    if authorization == "Bearer my-token":
        # Process the notification
        print(notification)
    return {"status": "received"}
```

Key points to remember:

- Primarily used in scenarios where network performance, location accuracy, or specific network capabilities are crucial.
- Common in IoT, autonomous vehicles, AR/VR applications, and industries requiring guaranteed network performance.

Regular APIs:
- Used across a wide range of applications and services, from web and mobile apps to enterprise software integrations.

8. Standardization:

Network APIs:
- Often adhere to telecom industry standards and protocols, ensuring interoperability across different network providers.

Regular APIs:
- May follow various standards depending on the industry and purpose, but generally have more flexibility in their design and implementation.

In summary, while regular APIs provide interfaces for software-to-software communication across a wide range of applications, network APIs specifically enable applications to interact with and leverage core network capabilities, offering unique features that can significantly enhance application performance, security, and functionality in network-dependent scenarios.

Regarding net neutrality principles in this context:

Net neutrality is the principle that internet service providers (ISPs) should treat all internet traffic equally, without discriminating or charging differently based on user, content, website, platform, application, type of equipment, or method of communication.

The use of Network as Code APIs, particularly the Quality of Service on Demand API, raises some interesting questions in relation to net neutrality:

1. Prioritization: Using QoD to boost network performance for specific applications could be seen as a form of traffic prioritization, which is generally against net neutrality principles.

2. Paid Prioritization: If ride-sharing companies pay for better network performance, it could be interpreted as "paid prioritization," which is often considered a violation of net neutrality.

3. Equal Access: Smaller competitors who can't afford to pay for enhanced network services might be at a disadvantage, potentially conflicting with the idea of an open and equal internet.

4. Transparency: The use of these APIs should be transparent to users and regulators to ensure compliance with net neutrality regulations.

5. User Choice: It's important to consider whether users have a choice in the use of these network enhancements, or if they're applied universally.

6. Network Management: Proponents might argue that these APIs represent legitimate network management practices, especially if they're used to ensure service quality in congested or underserved areas.

7. Innovation vs. Regulation: There's an ongoing debate about balancing innovation in network technologies with maintaining an open internet.

It's worth noting that the application of net neutrality principles to mobile networks and specialized services can be complex and may vary by jurisdiction. In some cases, reasonable network management practices are allowed even under strict net neutrality rules.

For ride-sharing applications to use these APIs responsibly and in compliance with net neutrality principles, they should:

1. Ensure transparent use of any network prioritization
2. Apply enhancements equally to all users of the service
3. Not degrade service for non-users or competitors
4. Use enhancements primarily for improving overall service quality rather than gaining competitive advantage

The use of Network as Code APIs in this context highlights the ongoing challenge of balancing technological innovation with principles of open and equal internet access.
