When creating a Quality-on-Demand (QoD) session, you need to include both public and private IP addresses, along with a public port, to accurately identify the device. This is crucial because devices often use Network Address Translation (NAT) technology.

Devices cannot be identified solely by their public IPv4 address. To ensure unique identification, you must provide either:
*   The device's public IP address and public port.
*   The device's public IP address and private IP address.

This combination allows the Nokia Network-as-Code platform to correctly identify and program the network for the specific device, even when it is behind a NAT gateway.

Question: How does network as code handle end-user consent?

Response:

Nokia Network-as-Code (NaC) handles end-user consent with a privacy-by-design approach, ensuring compliance with data protection regulations like GDPR. Consent management in NaC involves granting or revoking an application's access to APIs and their parameters, allowing authorized devices to be used safely.

There are two primary consent flows:

1.  **Client Initiated Backchannel Authentication (CIBA) Flow**:
    *   In simpler cases, NaC handles end-user requests using CIBA.
    *   An Authorization Server guards access to the end-user device and is polled by NaC until a response is provided.
    *   The Authorization Server triggers an end-user consent request, which the user can approve or deny.
    *   Upon approval, a client token is provided, authorized to perform the desired action.
    *   From the developer's perspective, this flow is largely transparent, with NaC runtime managing the polling for access tokens. Developers may need to adjust API request timeouts as consent approval can take some time.

2.  **Authorization Code Flow**:
    *   This flow is used when the end-user needs to take positive action to indicate their consent.
    *   The application developer constructs an authorization URL pointing to the NaC authorization server, including their own redirect handler.
    *   The end-user application, running on the end-user device, is directed to this URL.
    *   NaC then redirects the user to their operator-specific consent portal to approve the request.
    *   If consent is given, the application is redirected back to its redirect URI with an operator code.
    *   This code is then exchanged for a single-use access token, which is passed with subsequent API requests to validate user consent.

**B2B Consent Scenarios**:
For Business-to-Business (B2B) scenarios, such as an enterprise owning multiple devices, an Organization Admin submits an authorization request via email to `support.networkascode@nokia.com`. This request uses a specific template to list:
*   Device IDs (phone numbers or email-like identifiers).
*   API scopes (e.g., `qod-sessions`, `location-verification`).
*   Authorized parties (organizations or system integrators).
*   Operators.
*   Consent start and revocation dates.
The NaC Admin validates this data with the operators to enable access.

**Application Registration and Consent**:
During application registration, developers must submit information about their business and the network capabilities they intend to use. This includes providing screenshots of the consent request flow that users will interact with. This ensures that the application asks for end-user consent in line with data privacy legislation, especially for personal information like location data or phone numbers.

Question: What do I need to do to my application in order to be able to receive notifications from Network as Code?

Response:

To receive notifications from Nokia Network-as-Code (NaC), you need to configure your application to act as a webhook receiver. This involves setting up an HTTP endpoint that can listen for and process incoming `POST` requests from the NaC platform.

Here's what you need to do:

1.  **Set up a Notification URL (Webhook Endpoint)**:
    *   Your application must expose an HTTP endpoint (e.g., `https://your-app.com/notifications` or `http://notify.me/here`) that NaC can send `POST` requests to.
    *   This endpoint will be the "notification URL" you provide when subscribing to specific NaC events (e.g., device connectivity status, QoD session updates, slice lifecycle events).

2.  **Implement an HTTP POST Handler**:
    *   Within your application, you need to write code that handles incoming `POST` requests to this designated URL.
    *   The NaC platform will send notification data in the request body, typically as a JSON payload. Your handler should be able to parse this JSON.

3.  **Configure an Authentication Token**:
    *   For security, you should provide a `notification_auth_token` when subscribing to notifications. NaC will include this token in the `Authorization` header of the `POST` request (e.g., `Bearer my-token`).
    *   Your application's endpoint should validate this token to ensure that the notification is coming from an authorized source.

4.  **Process the Notification Payload**:
    *   The structure of the notification payload will vary depending on the type of event you are subscribing to (e.g., device status, slice updates).
    *   You will receive a notification object containing details like `id`, `source`, `type`, `time`, and a `data` field that holds the event-specific information.
    *   Your application can then react to these changes based on the content of the notification object.

**Example (Conceptual Python using FastAPI):**

```python
from fastapi import FastAPI, Header
from pydantic import BaseModel
from typing import Annotated, Union

app = FastAPI()

# Define a Pydantic model for the incoming notification structure
# This structure will vary based on the specific notification type
class Data(BaseModel):
    # Example fields for a device status notification
    device: dict
    subscriptionId: str
    # ... other relevant fields

class Notification(BaseModel):
    id: str
    source: str
    type: str
    specversion: str
    datacontenttype: str
    time: str
    data: Data # This 'data' field will contain the event-specific payload

@app.post("/notifications")
async def receive_notification(
    notification: Notification,
    authorization: Annotated[Union[str, None], Header()] = None
):
    # Validate the authorization token
    if authorization == "Bearer my-token": # Replace "my-token" with your actual notification_auth_token
        print(f"Received notification: {notification.type}")
        print(f"Notification data: {notification.data}")
        # Implement your application's logic here to react to the notification
        return {"message": "Notification received successfully"}
    else:
        return {"message": "Unauthorized"}, 401

# To run this, you would typically use a server like Uvicorn:
# uvicorn your_app_file_name:app --port 8000
```

Question: What is a code example that uses QoD API?

Response:

Here is a Python code example demonstrating how to create a Quality-on-Demand (QoD) session with a specified duration and then extend it using the Nokia Network-as-Code (NaC) SDK.

```python
import network_as_code as nac
from network_as_code.models.device import DeviceIpv4Addr

# Initialize the Network as Code client with your application key
# Replace "YOUR_TOKEN" with your actual application key from the Dashboard
client = nac.NetworkAsCodeClient(token="YOUR_TOKEN")

# Identify the mobile network device for which the QoD session will be created
# Devices can be identified by public/private IP addresses and port, or phone number.
# The phone number does not accept spaces or parentheses.
device = client.devices.get(
    ipv4_address=DeviceIpv4Addr(
        public_address="1.1.1.2",
        private_address="1.1.1.2",
        public_port=80
    ),
    phone_number="+36721601234567"
)

# Create a QoD session for the identified device
# This session will prioritize traffic to "5.6.7.8" with a "QOS_L" profile for 3600 seconds (1 hour).
qod_session = device.create_qod_session(
    service_ipv4="5.6.7.8",
    profile="QOS_L",
    duration=3600
)

print(f"QoD Session created with ID: {qod_session.session_id}")
print(f"Initial duration: {qod_session.duration} seconds")

# Extend the duration of the existing QoD session by an additional 300 seconds (5 minutes)
qod_session.extend(300)

print(f"QoD Session extended by 300 seconds.")
print(f"New duration (if updated immediately): {qod_session.duration} seconds")
```

**Explanation of Parameters:**

*   `token`: Your application key, obtained from your Nokia Network-as-Code Dashboard.
*   `ipv4_address`: An object specifying the device's public and private IPv4 addresses and public port. This is crucial for identifying devices, especially those behind NAT.
*   `phone_number`: The phone number associated with the device, used for identification.
*   `service_ipv4`: The IPv4 address of the application server or service that requires the enhanced Quality of Service.
*   `profile`: The Quality of Service (QoS) profile (e.g., "QOS\_L") that indicates the desired connection type and prioritization.
*   `duration`: The length of the QoD session in seconds. This parameter is mandatory when creating a session.
*   `extend(300)`: A method called on an existing `qod_session` object to add 300 seconds to its current duration.

*Sources:*
* Source: https://developer.networkascode.nokia.io/docs/quality-on-demand/session-duration

Interpreting Network Insights API responses from Nokia Network-as-Code (NaC) primarily involves understanding the structure of the JSON objects returned, especially for congestion levels and notifications.

Here's how to interpret the responses:

### General Structure for Notifications (e.g., Congestion Notifications)

For event-driven notifications, the JSON schema typically follows a common pattern, providing metadata about the event itself:

*   **`id`**: A unique string value representing the event subscription identifier.
*   **`source`**: A string indicating where the event originated, often including the NaC API implementation and subscription ID (e.g., `org.camaraproject.congestioninsights.v0.event`).
*   **`type`**: A string value returned by the API, indicating the status or nature of the event (e.g., `event`).
*   **`specversion`**: A string representing the specification version of the event.
*   **`datacontenttype`**: Indicates the media type for the event payload encoding, which is typically `"application/json"` for CAMARA APIs.
*   **`time`**: A string value in ISO 8601 format (e.g., `2023-08-20T21:01:02.345Z`) indicating when the event occurred.
*   **`data`**: This is an object that contains the specific details of the event, such as congestion level data.

### Interpreting Congestion Level Responses

When querying for congestion levels (current, historical, or predictive), the response will contain an array of congestion level objects, each providing specific details:

*   **`level`**: This is a crucial string value indicating the congestion status experienced by the device. Possible values are:
    *   **"None"**: No congestion detected.
    *   **"Low"**: Low level of network congestion.
    *   **"Medium"**: Moderate network congestion.
    *   **"High"**: High level of network congestion.
*   **`confidence`**: This parameter is included for predictive congestion results. It's a numeric value ranging from 0 to 100, representing the percentage confidence in the prediction. A higher number indicates greater certainty in the predicted congestion level.
*   **`start`**: For historical or predictive data, this is an ISO 8601 formatted date string indicating the start timestamp for the congestion data.
*   **`end`**: For historical or predictive data, this is an ISO 8601 formatted date string indicating the end timestamp for the congestion data.

Question: What is a code example that uses QoD API?

Response:

Here is a TypeScript code example demonstrating how to create a Quality-on-Demand (QoD) session with a specified duration and then extend it using the Nokia Network-as-Code (NaC) SDK.

```typescript
import { NetworkAsCodeClient, DeviceIpv4Addr } from "network-as-code";

// Initialize the Network as Code client with your application key
// Replace "YOUR-TOKEN" with your actual application key from the Dashboard
const client = new NetworkAsCodeClient("YOUR-TOKEN");

// Identify the mobile network device for which the QoD session will be created
// Devices can be identified by public/private IP addresses and port, or phone number.
// The phone number does not accept spaces or parentheses.
const device = client.devices.get({
  ipv4Address: {
    publicAddress: "1.1.1.2",
    privateAddress: "1.1.1.2",
    publicPort: 80,
  },
  phoneNumber: "+36721601234567"
});

// Create a QoD session for the identified device
// This session will prioritize traffic to "5.6.7.8" with a "QOS_L" profile for 60 seconds.
const qodSession = await device.createQodSession("QOS_L", {
  serviceIpv4: "5.6.7.8",
  // serviceIpv6: "2041:0000:140F::875B:131B", // Optional IPv6 service address
  duration: 60, // Duration in seconds
});

console.log(`QoD Session created with ID: ${qodSession.sessionId}`);
console.log(`Initial duration: ${qodSession.duration} seconds`);

// Extend the duration of the existing QoD session by an additional 300 seconds (5 minutes)
await qodSession.extendSession(300);

console.log("QoD Session extended by 300 seconds.");
// Note: The qodSession object might not immediately reflect the extended duration
// without another API call to retrieve the updated session details.
```

**Explanation of Parameters:**

*   `NetworkAsCodeClient("YOUR-TOKEN")`: Initializes the client with your application key.
*   `device.get(...)`: Identifies the target mobile device using its IPv4 address details (public address, private address, public port) and phone number.
*   `device.createQodSession("QOS_L", {...})`: Creates a QoD session.
    *   `"QOS_L"`: Specifies the Quality of Service profile.
    *   `serviceIpv4: "5.6.7.8"`: The IPv4 address of the application server requiring the QoS.
    *   `duration: 60`: The initial duration of the session in seconds.
*   `qodSession.extendSession(300)`: Extends the active QoD session by an additional 300 seconds.

Question: What is the difference between network APIs and regular APIs?

Response:

Within the context of Nokia Network-as-Code (NaC), the distinction between network APIs and regular APIs lies primarily in their domain of operation and the capabilities they expose.

**Network APIs (as offered by Nokia NaC):**
These APIs are specifically designed to expose and control the underlying telecommunications network infrastructure, particularly 5G capabilities. They allow applications to directly interact with and program the network itself.

*   **Domain:** Operate directly on the network infrastructure (e.g., 5G core, radio access network).
*   **Capabilities:** Expose native network functionalities such as:
    *   **Quality of Service (QoS) on Demand:** Dynamically request specific bandwidth and latency guarantees for an application.
    *   **Device Location:** Retrieve precise geographic coordinates of a device.
    *   **Network Slicing:** Customize and allocate dedicated portions of the network for specific use cases (e.g., VR, XR).
    *   **Device Status:** Obtain real-time connectivity status of a device.
    *   **Congestion Insights:** Gain information about network congestion.
    *   **Identity and Security:** Features like SIM Swap detection and Number Verification for fraud prevention.
*   **Purpose:** To make the network programmable and adaptable to application requirements, enabling applications to be "network-aware" and optimize resource usage. They abstract the complexity of telecom networks, making them accessible to developers without specialized telecom expertise.
*   **Impact:** Allows for the creation of innovative services that dynamically respond to network conditions, optimize performance, and enhance security at the network level.

**Regular APIs:**
This is a broad term that generally refers to Application Programming Interfaces that expose functionalities of a software application, database, or web service. While they use the network for communication, they do not typically program or control the network's behavior.

*   **Domain:** Operate at a higher software layer, exposing features of a specific application, service, or data source.
*   **Capabilities:** Can include a vast range of functionalities, such as:
    *   Retrieving data from a database (e.g., weather data, product information).
    *   Sending notifications (e.g., email, SMS).
    *   Processing payments.
    *   Interacting with social media platforms.
    *   Managing cloud computing resources (e.g., creating virtual machines).
*   **Purpose:** To enable different software systems to communicate, exchange data, and invoke functions from each other, facilitating integration and modular development.
*   **Impact:** Powers most modern web and mobile applications by allowing them to leverage external services and data without needing to build everything from scratch.

**Key Differences Summarized:**

| Feature             | Network APIs (Nokia NaC)                               | Regular APIs                                              |
| :------------------ | :----------------------------------------------------- | :-------------------------------------------------------- |
| **Focus**           | Programming and controlling the underlying network     | Exposing application/service functionalities              |
| **Interaction**     | Direct interaction with network infrastructure         | Interaction with software applications/databases          |
| **Capabilities**    | QoS, slicing, device location, network status, etc.    | Data retrieval, payment processing, notifications, etc.   |
| **Network Control** | Actively modifies or requests network behavior         | Uses the network as a transport layer; does not control it |
| **Expertise**       | Abstracts telecom complexity for developers           | Requires expertise in the specific application/service    |

In essence, while regular APIs allow applications to *use* the network to communicate, network APIs empower applications to *program* and *influence* the network's behavior to meet specific performance, security, and connectivity requirements.

To enable your application to receive notifications from Nokia Network-as-Code (NaC), you need to configure a notification URL (often referred to as a webhook) and implement a handler within your application to process these incoming notifications.

Here's what you need to do:

1.  **Set up a Notification URL (Webhook)**:
    Your application must expose an HTTP or, preferably, an HTTPS endpoint that NaC can send notifications to. This URL will be provided to NaC when you subscribe to specific events (e.g., device status updates, slice state changes, geofencing events). NaC will then send POST requests to this URL whenever a relevant event occurs.

2.  **Provide a Notification Authentication Token**:
    When subscribing to notifications, you will also provide a `notification_auth_token`. This token acts as a password that NaC will include in the notification request (typically in the `Authorization` header). Your application's notification handler should verify this token to ensure that the notification is genuinely from NaC and not a malicious third party.

3.  **Implement a Notification Handler in Your Application**:
    Your application needs to have a server-side component that listens for incoming POST requests at the configured notification URL. This handler will:
    *   Receive the notification payload, which is typically in JSON format.
    *   Validate the `notification_auth_token` to authenticate the sender.
    *   Parse the notification's content to understand the event (e.g., device roaming status, slice state change).
    *   Implement logic to react to the specific event as required by your application.

**Example of how to configure a notification URL and token when subscribing (Python):**

When subscribing to a device connectivity status, you would specify these parameters:

**Example of a Python notification handler using FastAPI:**

```python
# status_handler.py
# run with: uvicorn status_handler:app

from fastapi import FastAPI, Header
from pydantic import BaseModel
from typing_extensions import Annotated
from typing import List, Union

app = FastAPI()

class Device(BaseModel):
    phoneNumber: str | None
    networkAccessIdentifier: str | None
    ipv4Address: str | None
    ipv6Address: str | None

class RoamingEventDetail(BaseModel):
    device: Device
    subscriptionId: str
    roaming: bool | None
    countryCode: int | None
    countryName: List[str] | None
    terminationReason: str

class Event(BaseModel):
    eventTime: str
    eventDetail: RoamingEventDetail

class Data(BaseModel):
    device: Device
    subscriptionId: str
    roaming: RoamingEventDetail

class RoamingStatusNotification(BaseModel):
    id: str
    source: str
    type: str
    specversion: str
    datacontenttype: str
    time: str
    eventSubscriptionId: str
    event: Event

@app.post("/notifications")
def receive_notification(
    notification: RoamingStatusNotification,
    authorization: Annotated[Union[str, None], Header]
):
    if authorization == "Bearer my-token": # Verify your token here
        # Process the notification object
        print(notification)
        return {"status": "success"}
    else:
        return {"status": "unauthorized"}, 401
```

Since this script cannot automatically set up a publicly accessible server, the subscription part will use a placeholder URL. import network_as_code as nac

```python
def verify_nac_device_status_api(
    app_key: str,
    phone_number: str,
    notification_url: str = "https://example.com/nac-notifications",
    notification_auth_token: str = "your-secure-auth-token"
):
    """
    Verifies the functionality of the Nokia Network-as-Code Device Status API.

    Args:
        app_key (str): Your Nokia NaC application key.
        phone_number (str): The phone number of the device to test (e.g., "+36721601234567").
        notification_url (str): A placeholder URL for receiving notifications.
                                In a real test, this would be a URL to your running webhook server.
        notification_auth_token (str): The authentication token for your notification URL.
    """
    print("--- Starting NaC Device Status API Verification ---")

    try:
        # 1. Initialize the Network as Code client
        print("\n1. Initializing Network as Code client...")
        client = nac.NetworkAsCodeClient(token=app_key)
        print("   Client initialized successfully.")

        # 2. Create a Device object
        print("\n2. Creating Device object...")
        my_device = client.devices.get(phone_number=phone_number)
        print(f"   Device object created for phone number: {my_device.phone_number}")

        # 3. Attempt to subscribe to a connectivity status event
        print("\n3. Attempting to subscribe to connectivity status events...")
        # Set an expiration time for the subscription (e.g., 1 day from now)
        subscription_expire_time = datetime.now(timezone.utc) + timedelta(days=1)

        connectivity_subscription = client.connectivity.subscribe(
            event_type="org.camaraproject.device-status.v0.connectivity-data",
            device=my_device,
            subscription_expire_time=subscription_expire_time,
            notification_url=notification_url,
            notification_auth_token=notification_auth_token
        )
        print("   Connectivity subscription created successfully:")
        print(f"     Subscription ID: {connectivity_subscription.id}")
        print(f"     Event Type: {connectivity_subscription.event_type}")
        print(f"     Notification URL: {connectivity_subscription.notification_url}")
        print(f"     Expires: {connectivity_subscription.subscription_expire_time}")

        # 4. Attempt to get the device's current connectivity status (polling)
        print("\n4. Retrieving current device connectivity status...")
        connectivity_status = my_device.get_connectivity()
        print("   Device Connectivity Status retrieved successfully:")
        print(f"     Connected: {connectivity_status.connected}")
        print(f"     Last Known Status: {connectivity_status.last_known_status}")

        # 5. Attempt to get the device's current roaming status (polling)
        print("\n5. Retrieving current device roaming status...")
        roaming_status = my_device.get_roaming()

            print(f"     Country Name: {roaming_status.country_name}")

        print("\n--- NaC Device Status API Verification Completed Successfully ---")

    except AuthenticationException:
        print("\nERROR: Failed to authenticate. Please check your application key.")
    except NotFound:
        print("\nERROR: Resource not found. The device or subscription might not exist.")
    except APIError as e:
        print(f"\nERROR: An API error occurred: {e}")
        print("   This might indicate invalid input or an issue with the NaC API.")
    except ServiceError:
        print("\nERROR: There was an internal server error in the NaC API.")
    except Exception as e:
        print(f"\nAN UNEXPECTED ERROR OCCURRED: {e}")

    finally:
```

Question: What are network APIs and why should I use them?

Response:

Network APIs, in the context of Nokia Network-as-Code (NaC), are interfaces that expose the underlying capabilities of a network, making them programmable and accessible to application developers. Traditionally, networks have been static and opaque, operating as "black boxes" to applications. Network APIs change this by simplifying network programming and allowing developers, even those without deep telecom experience, to interact with native 5G capabilities through easy-to-use SDKs and API calls. These APIs abstract complex network functionalities, enabling applications to dynamically request and utilize network resources.

You should use Network APIs for several compelling reasons:

1.  **Enhanced Application Functionality and Innovation**: Network APIs enable the creation of new, innovative, and network-aware applications. By allowing applications to understand and react to network conditions, developers can build more intelligent and robust services across various industries, from autonomous vehicles to remote healthcare.
2.  **Dynamic Resource Optimization**: Applications can dynamically request and optimize network resources such as Quality of Service (QoS), bandwidth (upload/download ratios), and latency on demand. This ensures that applications receive the necessary network performance precisely when needed, leading to a more consistent and reliable user experience.
3.  **Cost Efficiency**: Instead of relying on expensive, always-on premium network plans, Network APIs allow applications and users to pay for premium network capabilities only when they are actively used. This optimizes costs by aligning network resource consumption with actual application requirements.
4.  **Greater Network Control and Awareness**: Developers gain increased control over programmable network features, including managing multiple devices, monitoring device locations, checking connectivity and roaming status, and gathering application telemetry. This level of control was previously unavailable to application developers.
5.  **Improved Security and Fraud Prevention**: APIs like SIM Swap and Number Verification provide powerful tools for enhancing security and preventing fraud. They enable applications to perform more robust authentication, verify user identities, and assess risk during sensitive transactions.
6.  **Simplified Development**: NaC SDKs abstract the complexity of network interactions, offering modern code patterns and a user-friendly way to integrate network capabilities. This significantly reduces the time and effort required for developers to leverage advanced network features.

In essence, Network APIs transform networks from static infrastructure into flexible, programmable platforms that applications can interact with, leading to better, more efficient, and innovative digital services.

Question: What is the difference between network APIs and regular APIs?

Response:

The distinction between Network APIs and "regular" APIs lies primarily in their domain of control, the type of functionalities they expose, and the underlying infrastructure they interact with.

**Regular APIs (Application Programming Interfaces in a general sense):**
*   **Domain:** These APIs typically expose the functionalities, data, or business logic of a specific software application, service, or platform.
*   **Interaction:** They allow different software systems to communicate and exchange data, enabling integration between various applications (e.g., a payment gateway API, a social media API, a mapping service API, a weather API).
*   **Focus:** Their primary focus is on application-level features, data manipulation, and service integration. They operate above the network infrastructure.
*   **Abstraction:** They abstract the internal workings of the software service they represent.

**Network APIs (as exemplified by Nokia Network-as-Code):**
*   **Domain:** Network APIs specifically expose and allow control over the underlying capabilities and resources of a telecommunications network (e.g., 5G network).
*   **Interaction:** They enable applications to directly interact with and influence network behavior and performance. This includes functionalities like Quality of Service (QoS) on Demand, network slicing, device location retrieval, device status monitoring, and fraud prevention mechanisms like SIM Swap detection.
*   **Focus:** Their primary focus is on making the network programmable and "application-aware," allowing applications to dynamically request and optimize network resources based on their real-time needs.
*   **Abstraction:** They abstract the immense complexity of telecom infrastructure, making advanced network capabilities accessible to developers who may not have deep telecommunications expertise.

**Key Differences Summarized:**

1.  **What they control/expose:**
    *   **Regular APIs:** Control and expose features/data of a software application or service.
    *   **Network APIs:** Control and expose capabilities and resources of the underlying network infrastructure.
2.  **Level of Operation:**
    *   **Regular APIs:** Operate at the application layer, facilitating inter-application communication.
    *   **Network APIs:** Operate closer to the network infrastructure layer, allowing applications to influence network behavior.
3.  **Purpose:**
    *   **Regular APIs:** To integrate software services, exchange data, and extend application functionalities.
    *   **Network APIs:** To make the network programmable, dynamic, and responsive to application requirements, enabling new network-aware services and optimizing resource usage.
4.  **Complexity Abstracted:**
    *   **Regular APIs:** Abstract the internal logic and data structures of a software service.
    *   **Network APIs:** Abstract the intricate complexities of telecommunications protocols, network functions, and infrastructure management.

In essence, while both are interfaces for programmatic interaction, Network APIs provide a unique bridge between the application world and the network world, allowing applications to actively shape and utilize network resources rather than just passively consuming network connectivity.

Question: Which Network as Code APIs can ride share applications like Uber use? How does the principles of net neutrality apply in this context?

Ride-sharing applications, such as Uber, can leverage several Nokia Network-as-Code (NaC) APIs to enhance their functionality, driver experience, and operational efficiency. These APIs allow the application to interact with the network dynamically.

Here are the NaC APIs that ride-sharing applications can utilize:

1.  **Quality of Service (QoS) on Demand (QoD)**:
    *   **Use Case:** A driver's application can dynamically request a bandwidth boost when approaching a busy location for passenger pickup or during critical navigation updates. This ensures stable connectivity and high performance, even in areas with network congestion.
    *   **Benefit:** Improves the reliability of real-time mapping, communication with passengers, and payment processing, leading to a smoother experience for both drivers and riders.

2.  **Device Location**:
    *   **Use Case:** The application can retrieve and verify the precise location of drivers and passengers. This is crucial for matching, navigation, and ensuring safety.
    *   **Benefit:** Enhances the accuracy of ride matching, optimizes routing, and provides better estimated times of arrival.

3.  **Network Insights**:
    *   **Use Case:** The driver application can receive current and predicted network congestion information. This allows the app to intelligently adapt, for example, by suggesting alternative routes to avoid areas with poor network quality or by triggering a QoD boost proactively.
    *   **Benefit:** Helps drivers maintain optimal connectivity and performance by anticipating and reacting to network conditions.

4.  **Device Insights**:
    *   **Use Case:** The application can check the connectivity status of a driver's device and receive notifications if the connection status changes.
    *   **Benefit:** Allows the application to be aware of and handle potential connectivity issues, ensuring that critical functions are not interrupted.

5.  **Specialized Networks (Slice Management)**:
    *   **Use Case:** In scenarios requiring highly reliable and low-latency connectivity for critical driver functions or safety features, the application could request to use a specific network slice.
    *   **Benefit:** Provides dedicated network resources with guaranteed QoS, which could be vital for autonomous features or critical safety alerts in the future.

These capabilities enable ride-sharing applications to be "network-aware," allowing them to adapt to changing network conditions and provide a more robust and reliable service.
